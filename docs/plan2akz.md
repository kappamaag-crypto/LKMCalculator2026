# plan2akz — основной план развития АКЗ-калькулятора v3

> **Живой план проекта.** После каждого существенного этапа статусы обновляются прямо здесь.
>
> **Главный приоритет:** **расчёт АКЗ → система покрытия → сравнение → Excel/PDF**.
>
> Ключевое требование: система покрытия поддерживает 2, 3, 4 и любое разумное количество слоёв. Legacy Excel на 2 слоя не является ограничением калькулятора v3.

## 0. Правила

1. Не ломать рабочий АКЗ-расчёт.
2. Расчётная логика остаётся в Domain/Service, не в UI.
3. Excel не становится вторым расчётным движком.
4. PDF и Excel получают данные из одного `CalculationResult`.
5. Инженерные и складские данные не смешиваются без необходимости.
6. Каждый существенный этап покрывается тестом/smoke-check.
7. Отдельный commit.
8. После commit обновляется этот план.

# I. ОСНОВНОЙ WORKFLOW АКЗ — КРИТИЧЕСКИЙ ПРИОРИТЕТ

## 1. Расчёт АКЗ

**[ВЫПОЛНЕНО, НО НУЖНО ПРОДОЛЖИТЬ]**

Есть расчёт слоёв, DFT/WFT, теоретический/практический расход, кг/м² и л/м², разбавитель, стоимость, площадь, `CalculationResult`, валидация и multi-layer расчёт.

Precision/regression покрывает отсутствие промежуточного округления, согласованность кг/л, масштабирование на площадь и разные основания разбавления.

## 2. Система покрытия на основном экране

**[ВЫПОЛНЕНО, НО НУЖНА ВИЗУАЛЬНАЯ ПРОВЕРКА]**

Целевой workflow: `Расчёт → система → проверка → сравнение → экспорт`.

Система динамическая по числу слоёв без архитектурного ограничения `layer1/layer2`.

Сделано на текущем этапе:
- добавление/удаление слоёв в редакторе системы;
- безопасная перестановка слоёв вверх/вниз с автоматической перенумерацией;
- сохранение порядка слоёв в `layer_number` и восстановление порядка при загрузке;
- из последнего успешного расчёта можно создать несохранённый черновик системы с тем же составом, DFT и разбавлением, после чего проверить/отредактировать и сохранить его в БД;
- расчёт передаётся в редактор системы через `SystemCalculationResult`, без повторного расчёта и без изменения расчётного движка;
- уже сохранённую систему можно скопировать в новый несохранённый черновик с сохранением состава слоёв и параметров DFT/разбавления;
- добавлен формальный Qt/UI regression для перестановки → сохранения → reload → копирования;
- добавлен UI regression для создания черновика системы непосредственно из последнего `SystemCalculationResult` без повторного расчёта;
- CI запускает Qt-тесты в headless-режиме через `QT_QPA_PLATFORM=offscreen`.

Коммиты текущего этапа:

- `dcdebf1ad8cd6cd150e0792398bdbca0bbb68e6` — кнопки ↑/↓ в редакторе сохранённых систем;
- `6f16fd66553bb6237314c1ca2088af16e236fa37` — создание черновика системы из последнего расчёта;
- `7e80e9fea4c0ce7518917a5f105781383bdc0d58` — передача последнего `SystemCalculationResult` в редактор систем;
- `e66d6ca2f6df623602b732205626ad61d3a080bd` — копирование сохранённой системы в новый черновик;
- `279b611f2a1c2de0eea6e9c6a27e2e9d07a5ccff` — UI regression для SystemsView;
- `3a4c0e48585ed9b8ce43640617d007aef703a1bf` — headless Qt CI для UI regression;

Проверка сохранения порядка покрыта тестом через реальный SQLite reload: после перестановки слой сохраняет новый `layer_number`, а новый экземпляр `SystemsView` восстанавливает тот же порядок. ## 4. Сравнение систем АКЗ

**[ВЫПОЛНЕНО, НО НУЖНА ВИЗУАЛЬНАЯ ПРОВЕРКА]**

Сравнение `CalculationResult` выполняется без повторного расчёта. Сохраняются 2/3/4+ слоёв. Исправлен двойной счёт разбавителя; отдельно показываются ЛКМ, разбавитель и итог. `compare_results()` блокирует смешение разных площадей. UI передаёт результат расчёта напрямую в `ComparisonView`.

Добавлен прозрачный технологический блок сравнения. Для каждой системы теперь выводятся рассчитанные по слоям ограничения:
- связующие;
- минимальная и максимальная температура нанесения как наиболее ограничивающее значение по слоям;
- минимальная/максимальная межслойная выдержка;
- максимальное время полного отверждения;
- максимальная относительная влажность;
- минимальный требуемый запас до точки росы.

Технологические значения не превращаются в «оценку качества»: это исходные ограничения из карточек материалов, агрегированные worst-case по системе. Для объяснения различий UI дополнительно сообщает, какая система тоньше/дешевле/имеет меньше слоёв, и поясняет, что стоимость нельзя сравнивать вне требований к среде эксплуатации.

Comparison Excel расширен тем же технологическим блоком, без складских и закупочных данных.

2К также покрыт в сравнении: он остаётся одним слоем, а стоимость ЛКМ + разбавителя не удваивается.

Regression добавлен на worst-case агрегацию технологических ограничений для многослойной системы.

Осталось: ручная визуальная проверка UI и финальная проверка формулировок технологических ограничений на реальных карточках материалов.

## 8. 2К материалы

**[ВЫПОЛНЕНО, НО ТЕХНОЛОГИЧЕСКИЕ ОГРАНИЧЕНИЯ ПЕРЕНЕСЕНЫ В §14]**

Базовый принцип: 2К-материал — **один готовый материал/один слой**, а не две расчётные позиции.

Подтверждено:
- `is_two_component=True` проходит `CalculationService` как один слой;
- 2К работает в системах 2/3/4/5 слоёв;
- 2К работает первым, средним и последним слоем;
- положительный физический расход сохраняется в кг/м² и л/м²;
- `MaterialMix` и компоненты A/B восстанавливаются из SQLite;
- `is_two_component` сохраняется ORM → Domain;
- 2К проходит `ComparisonEngine.compare_results()` как один слой;
- comparison не удваивает стоимость разбавителя;
- customer-facing Excel выводит 2К один раз и не выводит A/B закупочные данные;
- Engineering Excel выводит 2К один раз и не выводит A/B закупочные данные;
- PDF принимает 2К как один слой;
- правила единиц готовы: расчёт выполняется по готовому mixed material, без разбиения расхода на A/B.

CI multilayer 2К: `34437813196` — **success**. Export/2К regression также покрыт ранее перечисленными тестами.

Pot life / induction time не превращаются в расчёт расхода; если потребуется их контроль, это будет технологическая валидация в §14.

**Не требуется:** отдельный расчёт количества A/B, отдельная стоимость A/B, комплектность закупки или ERP-логика.

## 21. Совместимость ЛКМ — P1

**[ЧАСТИЧНО]**

На текущем этапе извлечена и зафиксирована **Таблица 1 «Совместимость ЛКМ с грунтовками»** из предоставленной пользователем картинки и публичной страницы Kraska.Expert. В источнике строка — наносимый слой, столбец — предыдущий/грунтующий слой; поэтому правило хранится направленно `previous → applied`. `+` означает совместимость, `1` — проверить адгезию из-за разных растворителей, `2` — требуется придание шероховатости. Пустая ячейка трактуется как **нет подтверждённых данных**, а не как запрет. Источник: `https://kraska.expert/compatibility-tables.html`.

Реализован `upload/app/domain/compatibility.py` с полной транскрипцией 18 строк и 17 колонок таблицы, включая отдельное представление двух строк с одинаковым обозначением «ЭП»: `alkyd_epoxy` и `epoxy`. Это важно: их нельзя схлопывать в один химический класс только по аббревиатуре.

Сопоставление с текущей моделью `BinderType` сделано только там, где оно однозначно:
- `эпоксид` → `epoxy`;
- `полиуретан` → `polyurethane`;
- `акрил` → `polyacrylic`;
- `эпоксидный эфир` → `epoxy_ester` (только там, где он присутствует как предыдущий слой в исходной таблице).

`алкид`, `цинк-этилсиликат` и `прочее/не указано` автоматически ни к одной строке таблицы не привязываются. Это намеренно: текущий `BinderType` слишком груб для безопасного различения, например, алкидно-акриловой, алкидно-уретановой, пентафталевой и других групп. Для таких материалов результат — `нет подтверждённых данных`, пока не появится явная химическая основа из TDS/технической документации.

Добавлены regression-тесты на:
- направленность `previous → applied`;
- `+`, `1`, `2` как разные статусы;
- неизвестные пары как `UNKNOWN`;
- безопасное отображение текущих `BinderType` без домыслов;
- отдельное поведение `эпоксидного эфира` как колонки источника.

`seed_compatibility()` больше не содержит ранее заданных общих предположений вроде «алкид → эпоксид/полиуретан». В БД записываются только пары, подтверждённые источником для тех семейств, которые текущая модель может представить однозначно; неизвестные пары не становятся разрешёнными по умолчанию.

Коммиты этапа:
- `bb1d4ef07cf7c314fe5e3e770b988a7ffcac5a7e` — `feat: add source-backed coating compatibility matrix`;
- `1073f9c337d94a2dd7adce30d4190f07dbf74491` — `fix: seed only source-backed compatibility pairs`;
- `8d2059eb39fa2bf46e0fc69f3855abf6b3f60584` — `test: assert source warning markers explicitly`.

**Важно:** этот этап ещё не утверждает, что правило Kraska.Expert является правилом конкретного производителя. Следующий P1-шаг — сопоставить применимость каждой пары с реальной химической основой/состоянием покрытия, TDS и технологическими ограничениями материалов, а затем вынести проверку всей системы в §22. Никаких инженерных запретов на основании одной пустой ячейки пока не добавляется.

## 22. Layer Compatibility Engine — P1

**[ЧАСТИЧНО]**

Базовый отдельный Domain engine реализован в `upload/app/domain/layer_compatibility.py`. Он не содержит UI/ORM-логики и не вмешивается в расчёт расхода.

Сейчас engine:
- проверяет каждый переход `слой N → слой N+1`;
- работает для 2/3/4+ слоёв без фиксированного числа позиций;
- возвращает отдельный `LayerTransitionResult` для каждого перехода;
- формирует worst-case статус всей системы по приоритету `запрещено > нет подтверждённых данных > предупреждение > разрешено`;
- сохраняет исходное правило, источник и текст причины для каждого перехода;
- выделяет `blocking_transitions` для всех переходов, которые нельзя считать безусловно разрешёнными;
- принимает `LayerCompatibilityContext` для будущих TDS-backed условий (`previous_is_cured`, `recoat_elapsed_h`, `surface_prepared`), но **не придумывает** правила по этим полям без источника;
- умеет проверять уже рассчитанный `SystemCalculationResult` через `check_result()` без повторного расчёта.

Regression `upload/tests/test_layer_compatibility.py` покрывает:
- многослойную систему и проверку всех соседних переходов;
- source-backed warning `2` («требуется придание шероховатости»);
- `UNKNOWN` для неподтверждённого/несопоставленного связующего;
- worst-case `UNKNOWN`, если хотя бы один переход не подтверждён;
- контроль количества контекстов для переходов;
- проверку `SystemCalculationResult` без запуска `CalculationService` повторно.

Коммиты:
- `2ba6b0e0ad73c953ee194c87bba8266857f1520e` — `feat: add layered coating compatibility engine`;
- `002bbe65e979c1b9e2dc9d807ec9ab4972497b20` — `test: align compatibility cases with source matrix`;
- `f6354fb4b6cdcdc30c33a4640e8c5e3a8f47e13d` — `feat: check compatibility directly from calculation result`;
- `b079786ecae4605fd8ed580bbab4930875e72b57` — `test: verify compatibility checks use calculated result`.

Остаётся до закрытия §22: связать engine с редактором системы/основным workflow, добавить TDS-backed условия для состояния отверждения и межслойной выдержки там, где они действительно указаны производителем, и затем добавить UI-предупреждение без скрытого изменения расчёта.
