# plan2akz — основной план развития АКЗ-калькулятора v3

> **Живой план проекта.** После каждого существенного этапа статусы обновляются прямо здесь.
>
> **Главный приоритет продукта:** **расчёт АКЗ → система покрытия → сравнение → Excel/PDF**.
>
> **Ключевое требование:** система покрытия должна поддерживать **2, 3, 4 и любое разумное количество слоёв**. Ограничение старого Excel-шаблона на 2 слоя не является ограничением калькулятора v3.
>
> Все дополнительные функции развиваются вокруг этого workflow и не должны его ломать.

## 0. Правила

Статусы:
- **[НЕ ВЫПОЛНЕНО]** — ещё не реализовано.
- **[ЧАСТИЧНО]** — реализована только часть.
- **[ВЫПОЛНЕНО, НО НУЖНО...]** — основная часть готова, есть конкретный остаток.
- **[ВЫПОЛНЕНО]** — реализовано и проверено.
- **[ЗАБЛОКИРОВАНО]** — нужен другой этап/решение.
- **[ОТЛОЖЕНО]** — сознательно перенесено.

Для каждого изменения:
1. не ломать рабочий АКЗ-расчёт;
2. расчётная логика остаётся в Domain/Service, не в UI;
3. Excel не становится вторым расчётным движком;
4. PDF и Excel получают данные из одного `CalculationResult`;
5. инженерные и складские данные не смешиваются без необходимости;
6. тест/smoke-check;
7. отдельный commit;
8. после commit обновляется `plan2akz.md`.

# I. ОСНОВНОЙ WORKFLOW АКЗ — КРИТИЧЕСКИЙ ПРИОРИТЕТ

## 1. Расчёт АКЗ

**[ВЫПОЛНЕНО, НО НУЖНО ПРОДОЛЖИТЬ]**

Уже есть: расчёт слоёв, DFT/WFT, теоретический/практический расход, кг/м² и л/м², разбавитель, стоимость системы, площадь и итоги, `CalculationResult`, несколько баз разбавления, валидация и отсутствие промежуточного округления в основном движке.

Осталось: precision/regression tests, полный контроль единиц, стабильный 2К pipeline, технологические проверки и прозрачный источник инженерных результатов.

**Обязательное требование:** расчёт должен работать не только для 2 слоёв, а для **3+ слоёв без потери точности и данных**.

## 2. Система покрытия на основном экране

**[ЧАСТИЧНО]**

Целевой workflow: `Расчёт → сформировать/получить систему → проверить → сравнить → экспортировать`.

Система должна быть **динамической по количеству слоёв**: минимум 2, 3, 4 и далее без архитектурного ограничения вида `layer1/layer2`.

Осталось:
- полноценная модель/UX системы;
- add/remove/reorder слоёв;
- 2+ слоя в одном расчёте;
- save/load/copy system с сохранением всех слоёв и их порядка;
- удобное получение системы из расчёта;
- one-click добавление результата в сравнение;
- минимизация переходов в БД;
- запрет silent truncation при любом количестве слоёв.

## 3. Материал из экрана расчёта

**[ВЫПОЛНЕНО, НО НУЖНО ДОПРОВЕРИТЬ]**

Сделано: `+ Материал` из расчёта, запись в БД, автоматическое добавление слоем в текущий расчёт, обновление каталогов, duplicate check по нормализованному имени и добавление существующего материала при дубле с информационным предупреждением.

Осталось: regression test duplicate normalization, проверка всех полей, перезапуск/сохранность, проверка систем, сравнения и экспорта.

## 4. Сравнение систем АКЗ

**[ВЫПОЛНЕНО, НО ПОКА НУЖНО РАСШИРИТЬ]**

Есть базовое сравнение и инженерный приоритет над ценой.

Сделано дополнительно:
- сравнение результатов из `CalculationResult` без повторного расчёта;
- сохранение полного состава 2/3/4+ слоёв;
- regression coverage для пар 2/2, 2/3, 3/4 и 4/5 слоёв;
- regression coverage для `compare_results()`;
- исправлено двойное прибавление стоимости разбавителя в таблице сравнения;
- в таблице разделены стоимость ЛКМ, стоимость разбавителя и итоговая стоимость ЛКМ + разбавитель;
- инженерный Excel comparison теперь выводит те же основные и послойные показатели, что и UI;
- экспорт comparison сохраняет все слои, включая 5-й и далее, без перехода на фиксированные 2 слоя;
- comparison export использует собственные площади/итоги каждого `SystemCalculationResult`, не пересчитывая результаты через общий объект;
- добавлена защита `compare_results()` от смешения предварительно рассчитанных систем с разной площадью объекта;

Осталось:

# II. EXCEL / PDF — ОСНОВНОЙ ВНЕШНИЙ РЕЗУЛЬТАТ

## 5. Excel — рабочий customer-facing экспорт

**[ВЫПОЛНЕНО, НО НУЖНО ДОПРОВЕРИТЬ]**

`КалькуляторЭКСЕЛЛЬ.xlsx` признан **реальным рабочим документом**, а не обычным шаблоном. Произвольный лист `Расчёт` не может считаться заменой.

**Новое решение v3:** customer-facing экспорт теперь содержит **одну таблицу**, без дублирования блока «Если стоимость в КГ» / «Если стоимость в литрах». В одной таблице сохраняются инженерные расходные показатели и оба ценовых поля (руб/кг и руб/л), поэтому пользователь может работать с материалами независимо от того, какая форма цены заполнена.

**Важно:** ограничение исходного `База` на 2 слоя относится только к историческому оформлению Excel. Экспорт v3 обязан поддерживать **2, 3, 4 и более слоёв** и не имеет права молча отбрасывать слои.

### 5.1. Аудит рабочего Excel

**[ВЫПОЛНЕНО]**

Проверен файл `КалькуляторЭКСЕЛЛЬ.xlsx`.

Фактическая структура исходника:
- 1 лист: `База`;
- 25 строк × 21 колонка;
- основной диапазон `B:R`;
- две исторические секции: `B1:R11` и `B15:R25`;

- имеются merged cells;
- формулы находятся непосредственно в старом документе;
- скрытых строк/колонок нет;
- print area не задана; portrait;
- исходный файл содержит полноценное форматирование, числовые форматы и клиентскую форму.

**Критический вывод:** историческое дублирование kg/l больше не переносится в новый customer-facing результат. На выходе используется только первый визуальный блок `База`, расширяемый для 3+ слоёв.

## 8. 2К материалы

**[ЧАСТИЧНО]**

Базовый принцип зафиксирован: 2К-материал рассматривается в расчёте как **один готовый материал/готовое покрытие**, а не как две отдельные позиции для расчёта расхода.

Подтверждено regression-тестами:
- материал с `is_two_component=True` проходит обычный `CalculationService` как один слой;
- 2К остаётся одним слоем в системах из **2, 3, 4 и 5 слоёв**;
- 2К корректно работает не только первым, но и в середине/последним слоем системы;
- каждый слой сохраняет положительный физический расход в кг/м² и л/м²;
- информационные `MaterialMix`/компоненты A/B восстанавливаются из SQLite без превращения их в закупочный расчёт;
- `is_two_component` сохраняется при ORM → Domain.

Реализована интеграция справочных данных:
- `MaterialComponentRepository.list_for_material()`;
- `MaterialComponentRepository.get()`;
- `MaterialMixRepository.get_for_material()`;
- преобразование ORM → Domain для `MaterialComponent` и `MaterialMix`.

Осталось:
- проверить 2К в comparison;
- проверить 2К в customer-facing Excel;
- проверить 2К в Engineering Excel;
- проверить 2К в PDF;
- проверить правила единиц и готового mixed material;
- при необходимости добавить технологическую валидацию pot life/induction time.

Основной расчёт для слоя:
- DFT/WFT;
- теоретический и практический расход готового смешанного материала;
- расход в кг/м² и л/м²;
- расход на заданную площадь;
- стоимость готового смешанного материала на м² и на площадь;
- использование 2К-материала как одного слоя внутри системы из 2, 3, 4, 5+ слоёв;
- корректное участие в сравнении и Excel/PDF.

**Не требуется:** отдельный расчёт количества компонента A и компонента B, отдельная стоимость A/B или вывод потребности каждого компонента. Соотношение компонентов может храниться как технологическое свойство материала, если оно необходимо для справочной информации/валидации, но не является отдельным расчётным результатом.

Использовать существующие `MaterialComponent`, `MaterialMix`, `Package` только в той степени, которая нужна для описания 2К-материала и его готового состояния. **Не превращать приложение в ERP.**

2К должен корректно работать как один материал внутри любого слоя и не ломать multi-layer pipeline, comparison и экспорт.

- защита от дублей и идемпотентность;
- локальная копия сохраняется после успешной отправки;
- диагностика ошибок без раскрытия секретов;
- тестирование без реальной отправки email.

**Ручной отправки не предусматривается.** Пользователь не должен нажимать отдельную кнопку для передачи истории или БД материалов.

### Безопасность

SMTP-реквизиты не хранить в коде, Git или открытом `settings.json`.

Использовать защищённое хранилище ОС/секретов либо защищённую конфигурацию. Применять TLS/SSL и таймауты. В логах не должно быть паролей, токенов и иных секретов.

Передавать только необходимые данные, без лишней персональной или конфиденциальной информации. Для трассировки 2–3 установок предусмотреть стабильный `source_id` устройства/установки.

### Release tests

Перед закрытием этапа проверить:
- восстановление очереди после перезапуска;
- временную недоступность интернета/SMTP;
- retry и backoff;
- отсутствие дублей;
- целостность JSON;
- отсутствие секретов в репозитории/логах;
- 2–3 независимые установки;
- сохранность локальной истории и БД материалов.
