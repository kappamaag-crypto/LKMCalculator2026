# plan2akz — основной план развития АКЗ-калькулятора v3

> **Статус документа:** живой план проекта. После каждого существенного этапа обновлять статусы прямо здесь.
>
> **Главный приоритет продукта:** расчёт АКЗ → сравнение систем → экспорт результата в Excel/PDF.
>
> Дополнительные функции (2К, фасовка, химическая стойкость, технология нанесения, нормативная база, история, рекомендации и т.д.) развиваются вокруг этого основного рабочего процесса и не должны ломать его.

---

## 0. Правила работы по plan2akz

### Статусы

- **[НЕ ВЫПОЛНЕНО]** — задача ещё не реализована.
- **[ВЫПОЛНЕНО]** — задача реализована и проверена.
- **[ВЫПОЛНЕНО, НО НУЖНО...]** — основная часть сделана, но есть конкретный остаток/улучшение.
- **[ЧАСТИЧНО]** — реализована только часть требований.
- **[ЗАБЛОКИРОВАНО]** — нельзя корректно завершить без другой задачи/решения.
- **[ОТЛОЖЕНО]** — сознательно перенесено на более поздний этап.

### Обязательное правило каждого изменения

1. Не ломать рабочий расчёт АКЗ.
2. Не переносить расчётную логику в UI.
3. Не делать Excel вторым расчётным движком.
4. PDF и Excel должны получать данные из одного `CalculationResult`.
5. Не смешивать инженерные и складские/закупочные данные без необходимости.
6. После этапа — тесты + smoke-check приложения.
7. Отдельный commit.
8. После commit — обновить этот файл и указать, что именно осталось.

# I. ОСНОВНОЙ WORKFLOW АКЗ — КРИТИЧЕСКИЙ ПРИОРИТЕТ

## 1. Расчёт АКЗ

**[ВЫПОЛНЕНО, НО НУЖНО ПРОДОЛЖИТЬ]**

Цель: пользователь на основном экране вводит параметры и получает корректный инженерный расчёт системы покрытия.

Уже есть:
- расчёт слоёв;
- DFT/WFT;
- теоретический и практический расход;
- кг/м² и л/м²;
- разбавитель;
- стоимость системы;
- площадь и итоговые значения;
- отдельная модель `CalculationResult`;
- несколько баз разбавления;
- валидация входных данных;
- расчёт без промежуточного округления в основном движке.

Осталось:
- довести precision/regression tests;
- проверить все единицы измерения;
- окончательно стабилизировать 2К pipeline;
- добавить технологические проверки;
- обеспечить прозрачность источника каждого инженерного результата.

**Критерий готовности:** один и тот же вход всегда даёт воспроизводимый инженерный результат независимо от UI и способа экспорта.

---

## 2. Работа с системой покрытия на основном экране

**[ЧАСТИЧНО]**

Нужно получить удобный workflow:

`Расчёт → получить/сформировать систему → проверить → добавить в сравнение → экспортировать`

Задачи:
- полноценное представление системы покрытия;
- добавление/удаление/перестановка слоёв;
- сохранение системы;
- загрузка системы;
- копирование системы как новой версии/варианта;
- понятное отображение параметров каждого слоя;
- получение системы непосредственно из расчёта;
- добавление текущего результата в сравнение одним действием;
- не требовать лишнего перехода в БД материалов.

---

## 3. Материалы из экрана расчёта

**[ВЫПОЛНЕНО, НО НУЖНО ДОПРОВЕРИТЬ]**

Реализовано:
- `+ Материал` непосредственно в расчёте;
- сохранение нового материала в БД;
- автоматическое добавление в текущий расчёт;
- обновление каталога материалов;
- доступ материала в других разделах;
- защита от дубликатов по нормализованному названию;
- при существующем названии — информационное предупреждение и добавление существующего материала в текущий расчёт.

Нужно:
- regression test для duplicate normalization;
- проверить все поля нового материала;
- проверить перезапуск приложения и сохранность материала;
- проверить материал в системах/сравнении/экспорте.

## 4. Сравнение систем АКЗ

**[ВЫПОЛНЕНО, НО НУЖНО РАСШИРИТЬ]**

Главная задача: сравнить несколько инженерно допустимых систем и выбрать вариант по понятным критериям.

Минимальный состав:
- система;
- количество слоёв;
- материалы;
- DFT/WFT;
- теоретический расход;
- практический расход;
- расход разбавителя;
- стоимость системы, руб/м²;
- площадь;
- итоговая стоимость — только там, где выбран коммерческий/полный режим.

Правила:
- нельзя считать «толще = лучше» автоматически;
- технически неподходящая система не должна выигрывать только по цене;
- инженерная пригодность должна иметь приоритет над score/стоимостью;
- сравнение не должно подтягивать ненужные складские данные.

Осталось:
- расширить сравнение 2К;
- добавить технологические показатели;
- добавить объяснение различий;
- проверить UX добавления результата из расчёта;
- regression tests.

**[ЧАСТИЧНО]**

Фильтры:
- среда;
- температура;
- химическая стойкость;
- технология;
- поверхность;
- совместимость слоёв;

После прохождения hard filters:
- стоимость;
- расход;
- количество слоёв;
- технологичность;
- доступность.

Весы score вынести в конфигурацию.

Каждая рекомендация должна объяснять причину выбора.
