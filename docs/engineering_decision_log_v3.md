# Engineering Decision Log — v3

Журнал фиксирует инженерные решения ветки `v3.0-engineering-upgrade`. Запись отражает фактически реализованное поведение; предположения и непроверенные технологические правила не переводятся в `KNOWN`.

## ED-001 — Domain/service boundary

**Решение:** расчётная и инженерная логика размещается в domain/service слоях, UI не является вторым местом расчёта.

**Основание:** единый расчётный результат должен использоваться всеми представлениями и экспортерами.

**Статус:** принято и реализовано.

## ED-002 — One calculation result for PDF/Excel

**Решение:** PDF и Excel получают данные из результата расчёта; экспорт не пересчитывает потребность самостоятельно.

**Основание:** исключить расхождение между отображением, PDF и Excel.

**Статус:** принято и реализовано в текущем engineering export workflow; визуальная/печатаемая acceptance-проверка остаётся открытой по плану.

## ED-003 — UNKNOWN is not a default

**Решение:** отсутствие подтверждённого источника, значения или применимости представляется как `UNKNOWN`, а не заменяется догадкой.

**Основание:** инженерные ограничения должны быть трассируемыми и доказуемыми.

**Статус:** принято; применяется в TDS/normative boundaries.

## ED-004 — SPKEFFA is read-only TDS source

**Решение:** `kappamaag-crypto/SPKEFFA` используется только как read-only источник TDS. Изменения в него из этого проекта не выполняются.

**Основание:** отделить источник технической документации от приложения-калькулятора.

**Статус:** принято и реализовано как архитектурное ограничение.

## ED-005 — Catalogue is candidate source, not TDS proof

**Решение:** файлы `Системы 1–4` являются каталогом кандидатов. Наличие строки в каталоге само по себе не подтверждает технологическую применимость.

**Основание:** каталог не заменяет TDS/нормативный документ.

**Статус:** принято; подтверждённые сценарные альтернативы допускаются только через confirmed + `tds_verified=KNOWN` boundary.

## ED-006 — Explicit confirmation before persistence

**Решение:** draft System Template проходит отдельный `CONFIRM` gate перед сохранением; `UNKNOWN` TDS не может стать подтверждённым шаблоном.

**Основание:** ручное подтверждение и provenance должны быть отделены от автоматического импорта.

**Статус:** принято и реализовано.

## ED-007 — Controlled LossProfile

**Решение:** потери являются явным параметром с приоритетом `losses_percent` → `LayerInput/SystemCalculator LossProfile` → legacy `default_losses`; legacy default равен 0.0 и не является скрытым инженерным коэффициентом.

**Основание:** исключить неявные инженерные допущения и сохранить обратную совместимость API.

**Статус:** принято и реализовано; §28 закрыт.

## ED-008 — TDS verification promotion gate

**Решение:** технологическое правило переводится в `KNOWN` только при наличии source identity, бинарного SHA-256 PDF, locator и явного applicability, после ручной проверки. Git blob SHA-1 не используется как SHA-256 PDF.

**Основание:** обеспечить нормативную трассируемость и не выдавать извлечённый текст за верифицированный TDS.

**Статус:** принято; фактические rule-by-rule TDS verification из SPKEFFA остаются открытыми по §14/§25.

## ED-009 — No GitHub Actions for this workflow

**Решение:** GitHub Actions не добавляются и не используются как часть текущего рабочего процесса.

**Основание:** текущий план предусматривает локальные/ручные проверки и отдельный общий прогон позже.

**Статус:** принято.
