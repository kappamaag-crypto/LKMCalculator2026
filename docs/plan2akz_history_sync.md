# plan2akz — история и автоматическая передача данных

## Цель

Для 2–3 пользователей предусмотреть надёжную схему:

`локальное сохранение → outbox/очередь → фоновая отправка → SMTP служебного ящика → email владельца`.

Email является транспортом доставки, а не основной БД. Источник истины остаётся локальным.

## 1. История сравнения АКЗ/ОГЗ

**[НЕ ВЫПОЛНЕНО]**

Сохранять локально каждое завершённое сравнение АКЗ, а после появления OGZ — и ОГЗ.

JSON должен сохранять:
- состав сравниваемых систем;
- все слои 2/3/4+ и их порядок;
- входные параметры;
- расчётные результаты;
- дату/время;
- версию калькулятора;
- версию формул/расчётного движка.

Передача:
- фоновая, без блокировки UI;
- локальная очередь `pending/sending/sent/failed`;
- retry с backoff;
- история не теряется при отсутствии сети/SMTP;
- после успешной отправки локальная копия сохраняется;
- ручная команда «Отправить историю сейчас»;
- диагностика последней отправки;
- защита от дублей и бесконечных retry.

## 2. Автоматическая передача базы материалов

**[НЕ ВЫПОЛНЕНО]**

Передавать владельцу согласованный JSON snapshot базы материалов через тот же SMTP-транспорт.

Не отправлять файл БД при каждом изменении. Использовать очередь и debounce/периодическую синхронизацию.

Экспорт должен включать необходимые свойства материалов, в том числе ценовые поля, плотность, сухой остаток, компоненты 2К и связанные инженерные данные.

Поддержать:
- полный snapshot;
- при необходимости delta-изменения;
- дату/версию последнего успешного экспорта;
- контроль целостности JSON;
- локальное сохранение независимо от результата email-доставки.

## 3. Общий фоновой SyncService

**[НЕ ВЫПОЛНЕНО]**

Создать один общий сервис фоновой синхронизации для:
- `comparison_history`;
- `materials_database`;
- будущих разрешённых типов данных.

Общий механизм:
- сериализация JSON;
- локальная outbox;
- SMTP/TLS;
- retry/backoff;
- статусы и диагностика;
- дедупликация/идемпотентность;
- тестирование без реальной отправки email.

## 4. Безопасность

SMTP-реквизиты не хранить в коде, Git или открытом `settings.json`.

Использовать защищённое хранилище ОС/секретов или защищённую конфигурацию. Применять TLS/SSL и таймауты. В логах не должно быть паролей, токенов и иных секретов.

Отправлять только необходимые данные, без лишней персональной или секретной информации.

## 5. Release tests

Перед закрытием этапа проверить:
- восстановление очереди после перезапуска;
- временную недоступность интернета/SMTP;
- retry и backoff;
- отсутствие дублей;
- целостность JSON;
- отсутствие секретов в репозитории/логах;
- 2–3 независимые установки;
- сохранность локальной истории и БД материалов.
